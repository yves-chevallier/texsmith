\author{}\date{}

\maketitle
TeXSmith bundles a single fragment, \tscodeinline{ts-\allowbreak{}code}, that can render fenced code blocks with four different engines:
\begin{description}
\item[{\tscodeinline{pygments} (default)}] highlights code with Pygments at render time and injects the generated macros into \tscodeinline{ts-\allowbreak{}code.sty}. No shell escape is required and the output works with \tslogo{XeLaTeX} and Tectonic. Not suited for editing the \LaTeX{} output directly.
\item[{\tscodeinline{listings}}] uses the \LaTeX{} \tscodeinline{listings} package inside a \tscodeinline{tcolorbox}. Good for pure \LaTeX{} workflows without shell escape, but no automatic line highlighting.
\item[{\tscodeinline{verbatim}}] plain \tscodeinline{fvextra}/\tscodeinline{Verbatim} output wrapped in a tcolorbox. Useful when you want zero styling or external dependencies.
\item[{\tscodeinline{minted}}] Enhanced version of listings that shells out to \tscodeinline{pygmentize}. This needs \tscodeinline{-\allowbreak{}-\allowbreak{}shell-\allowbreak{}escape} and is disabled by default for compatibility with sandboxed engines such as Tectonic.
\end{description}
\section{Choosing an engine}
If you need to use one, pick the engine in front matter or via the CLI template override:
\begin{tscode}[lang=yaml, engine=pygments]
\begin{Verbatim}[commandchars=\\\{\},breaklines, breakanywhere, commandchars=\\\{\}]
\PY{n+nn}{\PYZhy{}\PYZhy{}\PYZhy{}}
\PY{n+nt}{press}\PY{p}{:}
\PY{+w}{  }\PY{n+nt}{code}\PY{p}{:}
\PY{+w}{    }\PY{n+nt}{engine}\PY{p}{:}\PY{+w}{ }\PY{l+lScalar+lScalarPlain}{listings}\PY{+w}{  }\PY{c+c1}{\PYZsh{} verbatim | listings | minted | pygments}
\PY{n+nn}{\PYZhy{}\PYZhy{}\PYZhy{}}
\end{Verbatim}
\end{tscode}
\begin{tscode}[lang=bash, engine=pygments]
\begin{Verbatim}[commandchars=\\\{\},breaklines, breakanywhere, commandchars=\\\{\}]
texsmith\PY{+w}{ }input.md\PY{+w}{ }\PYZhy{}a\PY{+w}{ }code.engine\PY{o}{=}verbatim
\end{Verbatim}
\end{tscode}
The choice is global for a render. Inline code spans follow the engine too: \tscodeinline{pygments} highlights them in place, \tscodeinline{minted} wraps them in \tscodeinline{\textbackslash{}mintinline}, and \tscodeinline{listings}/\tscodeinline{verbatim} fall back to plain \tscodeinline{\textbackslash{}texttt\{…\}}.
\section{Inline code wrapping}
A fenced block always wraps: every engine is configured with \tscodeinline{breaklines} (and \tscodeinline{breakanywhere} for \tscodeinline{fvextra}), so a long line folds inside the box instead of running past it. An \emph{inline} span has no such luxury --- it sits in a justified paragraph and \TeX{} will not break it on its own, so a long identifier such as \tscodeinline{texsmith.core.conversion\_options} pushes into the margin.

The \tscodeinline{code.inline} section declares where such a span may break:
\begin{tscode}[lang=yaml, engine=pygments]
\begin{Verbatim}[commandchars=\\\{\},breaklines, breakanywhere, commandchars=\\\{\}]
\PY{n+nn}{\PYZhy{}\PYZhy{}\PYZhy{}}
\PY{n+nt}{press}\PY{p}{:}
\PY{+w}{  }\PY{n+nt}{code}\PY{p}{:}
\PY{+w}{    }\PY{n+nt}{inline}\PY{p}{:}
\PY{+w}{      }\PY{n+nt}{plain}\PY{p}{:}\PY{+w}{ }\PY{l+lScalar+lScalarPlain}{true}\PY{+w}{          }\PY{c+c1}{\PYZsh{} typeset inline code as plain \PYZbs{}texttt, no highlighting}
\PY{+w}{      }\PY{n+nt}{breaks}\PY{p}{:}\PY{+w}{ }\PY{l+s}{\PYZdq{}}\PY{l+s}{\PYZus{}./}\PY{l+s}{\PYZdq{}}\PY{+w}{        }\PY{c+c1}{\PYZsh{} insert a break opportunity after each of these characters}
\PY{n+nn}{\PYZhy{}\PYZhy{}\PYZhy{}}
\end{Verbatim}
\end{tscode}
\begin{description}
\item[{\tscodeinline{breaks}}] The characters after which an \tscodeinline{\textbackslash{}allowbreak} is inserted. Defaults to \tscodeinline{-\allowbreak{}}, which is what TeXSmith has always done. Use \tscodeinline{all} (or \tscodeinline{true}) for the full punctuation set \tscodeinline{-\allowbreak{}\_./\textbackslash{}:;,|@+=\&\#\%}, and \tscodeinline{none} (or \tscodeinline{false}) to disable breaking entirely. Letters, digits and whitespace are ignored: breaking mid-word hurts legibility more than a slight overflow. Breaks are inserted in highlighted spans too, between the Pygments macros rather than inside them, so the colours survive.
\item[{\tscodeinline{plain}}] When true, inline spans are rendered as \tscodeinline{\textbackslash{}texttt\{…\}} with no syntax colouring, whatever the engine --- the \enquote{simple mono} mode. Blocks keep their highlighting. This is the only way to get break opportunities under the \tscodeinline{minted} engine, whose \tscodeinline{\textbackslash{}mintinline} is verbatim and cannot host an \tscodeinline{\textbackslash{}allowbreak}; and a document that only has inline spans no longer requests the shell escape \tscodeinline{\textbackslash{}mintinline} would have needed.
\end{description}
Both keys work as CLI overrides as well:
\begin{tscode}[lang=bash, engine=pygments]
\begin{Verbatim}[commandchars=\\\{\},breaklines, breakanywhere, commandchars=\\\{\}]
texsmith\PY{+w}{ }input.md\PY{+w}{ }\PYZhy{}a\PY{+w}{ }code.inline.plain\PY{o}{=}\PY{n+nb}{true}\PY{+w}{ }\PYZhy{}a\PY{+w}{ }code.inline.breaks\PY{o}{=}\PYZus{}./
\end{Verbatim}
\end{tscode}
\section{Pygments pipeline details}
When \tscodeinline{code.engine=pygments}, TeXSmith runs Pygments during conversion and writes the highlighted \LaTeX{} directly into the \tscodeinline{code} environment. All required style definitions are collected once per render and injected into \tscodeinline{ts-\allowbreak{}code.sty}, so no external calls are made during \LaTeX{} compilation. Highlighted lines and line numbers from the Markdown source are preserved.

This engine is the most flexible and works with all \TeX{} engines supported by TeXSmith, including Tectonic.

Furthermore, it is much faster than \tscodeinline{minted} since it avoids shelling out during \LaTeX{} compilation.
\section{Shell-escape behavior}
Shell escape is requested automatically when the minted engine is active or other features need it. With \tscodeinline{pygments}, \tscodeinline{listings}, or \tscodeinline{verbatim}, \tscodeinline{.latexmkrc} will not add \tscodeinline{-\allowbreak{}-\allowbreak{}shell-\allowbreak{}escape}, keeping builds compatible with engines like Tectonic.
\begin{tscallout}[kind=note]
By default \TeX{} disables shell escape for security reasons. Only enable it if you trust the source of your documents. Shell escape allows \LaTeX{} to run arbitrary commands on your system during compilation. This behavior is strongly discouraged by the Tectonic team and disabled by default.
\end{tscallout}
