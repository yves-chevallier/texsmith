\section{High-Level Workflows}
TeXSmith exposes a thin, expressive façade over the lower-level conversion primitives. Mix and match Markdown, HTML, and template-aware documents without touching the CLI or re-implementing glue code.

This page showcases the building blocks you are most likely to use in scripts, services, or notebooks. All examples assume \tscodeinline{pip install texsmith} (or \tscodeinline{uv tool install texsmith}) plus any template packages you rely on.
\begin{tscallout}[kind=tip, title={Run the snippets}]
Save the examples into a file and execute them with \tscodeinline{uv run python example.py}. The snippets rely only on fixtures you create alongside the script.
\end{tscallout}

\subsection{Drive the pipeline with \tscodeinline{ConversionService}}
If you need the exact orchestration used by the CLI, rely on \tscodeinline{ConversionService}. It exposes two steps:
\begin{enumerate}
\item \tscodeinline{prepare\_documents(request)} splits inputs, parses each one into its IR, applies slot assignments, and returns a prepared batch.
\item \tscodeinline{execute(request, prepared=...)} runs the passes, resolves once, writes one body per slot, wraps them in the template, and produces a \tscodeinline{ConversionResponse} with the bundle plus emitted diagnostics.
\end{enumerate}
Compiling is a step of its own, and not a method of the service: \tscodeinline{texsmith.adapters.latex.build.build\_pdf(render\_result, engine=...)} hands the rendered project to Tectonic or latexmk, and \tscodeinline{texsmith.core.conversion.typst.build\_typst\_pdf(path)} to the Typst compiler.

Diagnostics reach a caller two ways: as they happen, through the emitter passed
on \tscodeinline{ConversionRequest.emitter} (the CLI passes a \tscodeinline{CliEmitter}, libraries get the
silent \tscodeinline{NullEmitter} by default, \tscodeinline{LoggingEmitter} forwards to \tscodeinline{logging}); and
afterwards, as the \tscodeinline{Diagnostic} records kept on each \tscodeinline{Document} --- or all of them
together on \tscodeinline{request.emitter.sink}, which is what \tscodeinline{-\allowbreak{}-\allowbreak{}strict} and
\tscodeinline{-\allowbreak{}-\allowbreak{}diagnostics-\allowbreak{}json} read. Those two, and \tscodeinline{-\allowbreak{}-\allowbreak{}deprecated}, are the CLI's own
reading of the same records, not fields of the request.

\tscodeinline{response.result} is a \tscodeinline{ConversionBundle} without a template and a
\tscodeinline{TemplateRenderResult} with one; \tscodeinline{response.bundle} and \tscodeinline{response.render\_result}
are the guarded accessors, and \tscodeinline{response.is\_template} says which applies.

\subsection{Reuse the same plumbing as the CLI}
\tscodeinline{texsmith} relies on these high-level primitives. Inspect the CLI command and you will notice the same API surface shown above. Scripts and command-line invocations stay aligned, and new features land in one place.

For a complete reference, browse the API browser or explore the source directly in \tscodeinline{src/texsmith/core/}.
\begin{tscallout}[kind=seealso]
\begin{itemize}
\item Command-line Overview explains how these APIs surface through Typer commands.
\item Core Engine documents the lower-level modules if you need to plug into diagnostics or templating internals.
\end{itemize}
